# Приклад: Персональний блог на Next.js

**Живий сайт:** https://next-blog-example-kohl.vercel.app

Приклад розв'язку Арени модуля «Цитадель Некст».
Next.js 16 (App Router) і TypeScript, статті у файлах `.mdx`,
без бази даних і без адмінки.

Дизайн-референс (необов'язковий, у завданні макета немає): [The Blog, A Web Personal Blog](https://www.figma.com/design/xY3BPhpNbC1PBFJkNZ8w2a/The-Blog---A-Web-Personal-Blog?node-id=614-352).
Свій застосунок можеш оформити як завгодно.

## Як запустити

```bash
npm install
npm run dev        # http://localhost:3000
npm run build      # продакшн-збірка
npm start          # підняти те, що зібралося (потрібно для перевірок нижче)
npm run lint       # eslint
npm run typecheck  # tsc --noEmit
```

## Структура

```
app/
  layout.tsx              спільний каркас: <html>, шапка, підвал, метадані
  page.tsx                головна — титул і блок «Останні статті»
  blog/page.tsx           список усіх статей із пошуком
  blog/[slug]/page.tsx    сторінка статті
  api/posts/route.ts      GET /api/posts — список у JSON
  not-found.tsx           сторінка 404
  error.tsx               "use client" — межа помилок
  sitemap.ts              /sitemap.xml зі списку статей
  robots.ts               /robots.txt
  globals.css             стилі за макетом
components/
  Header.tsx              серверний
  Footer.tsx              серверний
  PostCard.tsx            картка статті в чотирьох розкладках
  FeaturedPosts.tsx       блок «Останні статті» з макета
  PostSearch.tsx          "use client" — стан і події; список приходить пропом
lib/
  posts.ts                читання .mdx із диска (тільки сервер)
  site.ts                 ім'я автора, адреса сайту — одне джерело правди
  format.ts               formatDate: «2026-08-13» → «13 серпня 2026»
content/posts/*.mdx       самі статті
public/covers/*.jpg       обкладинки
eslint.config.mjs         next/core-web-vitals + next/typescript
```

## Як додати статтю

Створи файл у `content/posts/`, наприклад `moya-nova-stattya.mdx`:

```mdx
---
title: "Моя нова стаття"
date: "2026-08-20"
excerpt: "Один рядок опису — його видно на картці й у пошуковій видачі."
cover: "/covers/moya-nova-stattya.jpg"
tags: ["Next.js"]
---

Текст статті у звичайному Markdown.
```

Підключений `remark-gfm`, тому в тексті працюють таблиці, `~~зачеркнутий
текст~~`, чеклісти й автопосилання з голої адреси. Без цього плагіна
таблиця мовчки лишилася б рядком з рисками — без жодної помилки
при складанні.

Після `git push` стаття з'являється на сайті, і код правити не треба.

Ім'я файла стає адресою: `moya-nova-stattya.mdx` → `/blog/moya-nova-stattya`.

## Що перевіряє ментор

Критерії Арени, слово в слово з завдання:

1. Є щонайменше три сторінки, серед них динамічна `[slug]`, і API-роут
   `route.ts` із методом `GET` віддає JSON.
   Тут це `/`, `/blog`, `/blog/[slug]` і `/api/posts`.
2. Серверний компонент отримує дані напряму, а не через `fetch` до
   власного `/api`; `"use client"` стоїть лише там, де є стан, ефекти
   чи обробники подій.
   Тут сторінки викликають `getAllPosts()` з `lib/posts.ts`, і той самий
   виклик стоїть у `app/api/posts/route.ts`.
3. `tsc --noEmit` проходить без помилок, у коді немає `any`, а посилання
   `*.vercel.app` з опису PR відкривається й показує всі сторінки.

## Як здати

1. Працюй в окремій гілці, наприклад `git switch -c nextjs-blog`.
2. Роби кілька змістовних комітів, а не один на весь проєкт.
3. Задеплой на Vercel (кроки нижче, у «Деплой на Vercel»).
4. Відкрий pull request і напиши в описі:
   - живе посилання Vercel;
   - адресу API-роута, щоб ментор побачив, що він працює. Тут це
     https://next-blog-example-kohl.vercel.app/api/posts;
   - кілька рядків про структуру `app/`: які є сторінки, де лежить
     `layout.tsx`, який компонент серверний, а який клієнтський і чому.

## Корисно знати

Це не критерії, а місця, де найчастіше помиляються.

**1. `params` — це проміс.**

```tsx
type PageProps = { params: Promise<{ slug: string }> };

export default async function PostPage({ params }: PageProps) {
  const { slug } = await params;   // ← без await тут undefined
```

Найчастіша помилка в цьому завданні, і найпідступніша: `params.slug` дає
`undefined`, файл не знаходиться, сторінка чесно віддає 404 — і жодної
помилки в консолі. Про це навіть написана окрема стаття
у самому блозі: `content/posts/params-tse-promis.mdx`.

**2. `"use client"` — лише там, де потрібні стан, події або хуки.**
Клієнтських компонентів тут два, і обидва мусять ними бути: `PostSearch`
(поле пошуку має стан) і `error.tsx` (межа помилок у React буває тільки
клієнтською). Решта — серверні: вони виконуються під час складання
й у браузер не потрапляють узагалі. Поставити `"use client"`
у `layout.tsx` — означає відправити в браузер увесь сайт.

Зверни увагу, чого `PostSearch` **не** робить: він не завантажує список.
Статті читає серверна сторінка `/blog` і передає їх пропом. Зробити
навпаки — `useEffect` + `fetch("/api/posts")` — спокуса сильна й помилка
типова: у HTML сторінки не було б жодної статті (ні для пошуковика,
ні для того, у кого JS не завантажився), користувач бачив би спалах
«Знайдено статей: 0», а сам запит зайвий — дані вже лежать на диску
поруч зі сторінкою. Правило просте: дані збирає сервер, `"use client"`
дістається рівно тому шматку, де є стан і події.

**3. `lib/posts.ts` імпортує `node:fs` і тому ніколи не поїде в браузер.**
Next.js це перевіряє: спроба імпортувати цей файл із клієнтського
компонента ламає складання. У `PostSearch` тому стоїть саме
`import type { PostSummary }` — типи зникають під час компіляції.

**4. `generateStaticParams()` збирає сторінки статей наперед.**
Подивись на вивід `npm run build`: маршрути статей позначені `●  (SSG)`.
Без цієї функції вони були б `ƒ (Dynamic)` — тобто складалися б
під час першого запиту користувача.

**5. `generateMetadata` бере заголовок і опис із фронтматера.**
Перевір: `curl -s .../blog/params-tse-promis | grep '<title>'`.
Має бути назва статті, а не назва сайту.

**6. `preload` лише в тих зображень, що на першому екрані.**
У Next.js 16 цей проп замінив `priority`, який тепер позначений застарілим.
Обкладинка статті та перша картка на головній мають `preload`, решта карток
вантажиться ліниво. Якщо попередньо вантажити все, браузер качатиме
двадцять картинок водночас і жодну не покаже швидко.

## Дрібниці, які легко проґавити

- **Захист від path traversal** у `getPostBySlug`. Без перевірки на `..`
  і `/` адреса `/blog/..%2F..%2F.env` змусила б сервер прочитати чужий файл.
  Перевір: така адреса має давати 404.
- **`metadataBase`** у `layout.tsx` — з адреси в `lib/site.ts`. Без неї
  Next.js бере `http://localhost:3000` для картинок Open Graph, і посилання,
  яким поділилися, тягне обкладинку з чужого комп'ютера.
- **Ім'я автора живе в одному файлі** — `lib/site.ts`. Шапка, підвал
  і заголовок вкладки беруть його звідти. Поки кожен файл писав ім'я
  в себе, у шапці стояло одне, а на вкладці — інше; таке помічають
  не автори, а читачі.
- **`timeZone: "UTC"` у `formatDate`.** `new Date("2026-08-13")` — це
  північ за UTC, і без цього рядка дата показувалася б у поясі того, хто
  форматує: сервер у Києві сказав би «13 серпня», браузер у Нью-Йорку —
  «12 серпня».
- **Рівень заголовка картки — проп, а не константа.** На головній над
  картками стоїть `h2` «Останні статті», тому картки там `h3`.
  На `/blog` над сіткою одразу `h1`, тому картки — `h2`. Жорсткий `h3`
  давав би на `/blog` стрибок `h1 → h3`, а читалка повідомляє про
  пропущений рівень як про помилку.
- **`/api/posts` існує не для сторінок.** Сторінки серверні й читають
  статті напряму, без кола через мережу. Роут потрібен тим, хто ззовні:
  скрипт, стороння сторінка, `curl` під час перевірки. І він викликає
  той самий `getAllPosts()` — одна функція, однакові дані й однаковий
  порядок сортування скрізь.
- **`console.error` у `catch`** в `app/api/posts/route.ts`. Клієнту —
  статус і коротке повідомлення без подробиць, подробиці — в логи
  (на Vercel це вкладка Logs). `catch`, який не пише нікуди, ховає
  причину падіння назовсім.
- **Перевірка фронтматера** в `lib/posts.ts`. `gray-matter` віддає
  `Record<string, unknown>` — він не знає, що ти туди написав. Одруківка
  `titel` без перевірки дала б порожній заголовок замість помилки.
- **Клас шрифту стоїть на `<html>`, а не на `<body>`.** Змінну
  `--font-inter` читає правило для `:root` у `globals.css`, а `:root` —
  це саме `<html>`. На `<body>` змінна оголосилася б надто низько,
  і в `:root` лишився б Times.
- **`new Date().getFullYear()`** у підвалі. Сайт із «© 2023»
  виглядає покинутим.

## Як з макета виходять точні числа

Розмітка макета влаштована так: `Section (1440) → Container (1280,
padding 32) → контент (1216)`. Тому `.container` має `max-width: 1280px`
і `padding: 0 32px` — і контент усередині виходить рівно 1216, як у Figma.
Далі всі розміри просто збігаються: 3 колонки по 384 з проміжком 32,
обкладинки 240, компактна картка 320×200.

**Титул** у макеті має кегль 243.8px при контейнері 1216 — тобто рівно
20.05% його ширини. Саме це й записано в CSS:

```css
.hero {
  container-type: inline-size;
}

.hero__title {
  font-size: 20.05cqw;
}
```

`cqw` — відсоток ширини контейнера. Один рядок замість трьох `@media`,
і напис лишається на всю ширину і на моніторі, і на телефоні.

## Блок «Останні статті»

У макеті цей блок навмисно нерівномірний: перша стаття велика, дві
наступні компактні (обкладинка ліворуч, текст праворуч), четверта —
на всю ширину. Так око одразу бачить, що читати першим.

Уся ця нерівномірність — питання **CSS, а не розмітки**. Компонент картки
скрізь один і той самий (`PostCard`), змінюється лише проп `layout`:

```tsx
<PostCard post={lead} layout="lead" headingLevel={3} preload />
<PostCard post={post} layout="compact" headingLevel={3} />
<PostCard post={wide} layout="wide" headingLevel={3} />
```

Обкладинка великої картки не має власної висоти — вона забирає все, що
лишилося від висоти сусідньої колонки. Тому нижні краї обох колонок
збігаються, хоч тексти в них різної довжини.

## Кольори бейджів

У макеті бейджі семи кольорів, і на різних картках однакові підписи
пофарбовані по-різному. Тут колір рахується з тексту тегу:

```tsx
function badgeTone(tag: string): number {
  let sum = 0;
  for (const char of tag) sum += char.codePointAt(0) ?? 0;
  return (sum % 7) + 1;
}
```

Так «CSS» усюди на сайті одного кольору. Чергування через
`nth-child` цього не дало б: у кожної картки лічильник починається
спочатку, і далі за третій колір список ніколи не зайшов би.

## Деплой на Vercel

1. Залий репозиторій на GitHub.
2. На vercel.com → **Add New → Project** → обери репозиторій.
3. Налаштовувати нічого не треба: Vercel сам упізнає Next.js.
4. Після першого деплою підстав отриману адресу в `url` у `lib/site.ts`
   і зроби ще один push. Звідти її беруть і `metadataBase`, і `sitemap.xml`,
   і `robots.txt` — правити треба один рядок.

## Відмінності від дизайн-референсу

Макет тут лише референс: завдання його не вимагає. Ось де сайт від нього
відходить і чому.

- **Титул** — «МІЙ БЛОГ» замість «THE BLOG». Розмір і поведінка ті самі.
- **Обкладинки** згенеровано програмно (абстрактні заливки в палітрі
  макета) замість фотостоку — щоб репозиторій не тягнув чужі зображення
  з невідомою ліцензією. Заміни їх на свої.
- **Перемикача теми з макета немає.** У макеті є тільки світла тема,
  а сама пігулка нічого не перемикає — це декорація. Кнопка, яка нічого
  не робить, гірша за її відсутність.
- **Ім'я автора біля кожної статті** з макета не переноситься: у блозі
  один автор, і повторювати його під кожним заголовком нема сенсу.
  Замість нього на картці лишається дата.
- **«Recent blog posts» і «All blog posts»** у макеті стоять на одній
  сторінці; тут вони розведені на `/` і `/blog`, бо завдання вимагає
  трьох окремих маршрутів.
- **Посилання «Головна» і «Статті»** у шапці макета немає — але без них
  до трьох маршрутів завдання не дійти.
- **Тексти українською.**

## Перевір себе перед здачею

Пункти 3–5 перевіряють зібраний сайт, тому спершу `npm run build`,
а потім `npm start` в окремому вікні терміналу.

1. `npm run build` — без помилок; статті позначені `●  (SSG)`.
2. Додай новий `.mdx`, перезапусти збірку — стаття з'явилася без правок коду.
3. `/blog/якась-дурниця` — сторінка 404, а не помилка сервера.
4. `curl -s localhost:3000/api/posts` — коректний JSON. Після деплою те
   саме має відкриватися на живій адресі, наприклад
   https://next-blog-example-kohl.vercel.app/api/posts.
5. `curl -s localhost:3000/blog | grep -c post-card__title` — не нуль.
   Список статей має бути в HTML, а не домальовуватися з браузера.
6. `npm run lint && npm run typecheck` — обидва без зауважень.
7. `grep -rl '"use client"' app components lib` — рівно два файли:
   `components/PostSearch.tsx` і `app/error.tsx`. Саме `-rl` (імена файлів),
   а не `-rn`: із `-rn` у вивід лізуть окремі рядки, і порахувати
   компоненти стає важче.
8. `grep -rn ': any\|as any' app components lib` — порожньо.
9. Консоль браузера порожня.
10. Переглянь сайт на трьох ширинах: 1440, 834 і 390.
